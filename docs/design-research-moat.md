# Mesa 后续设计方案：让人敢在 AI 的活上签字

> 状态：**2026-11-02 已拍板**（architecture §10 同日条）：本轮做 3.1 核验层、3.2 研究记录、3.3 研究档案；CLI 分级采纳（一等 Claude Code、
> Codex、Kimi）；本机统计做、默认不发；3.4 课题组、3.5 机构版等试点与客户再立项；科研包暂缓。§8 的 1–5 项按建议采纳，6、7 暂不立项，8（试点人选）待定。
> 另加一条「流程减负」线（§4.4）。落地细则随各期写进 `docs/conventions/pipeline.md` / `safety.md`。

## 0. 一句话

**AI 越强，人越需要放心。**Mesa 不和 Agent 比谁更会干活，而是做 AI 辅助研究的**记录与核验系统**：
哪家 Agent 干的活都在 Mesa 里留痕、被核验、由人签字；记录跟着课题走，年头越久越离不开。

判断一个新功能值不值得做，先问：**这件事的价值是 AI 越强越大，还是越小？**越小的少投入，越大的多投入。

## 1. 我们现在站在哪

### 1.1 外部局面

| 层 | 趋势 | 对 Mesa 的含义 |
|---|---|---|
| CLI 外壳（会话、worktree、后台任务、配置） | Claude、Codex 都在做自家桌面端，越做越全 | 贬值层，保持能用、不再加大投入 |
| 流程编排（把研究拆成固定步骤） | 模型能自己规划长任务，固定步骤会变成负担 | 逐步从「步骤」转向「检查点」 |
| 文献检索与数据 | Elicit、SciSpace、各家 Deep Research 有索引与全文 | 不拼数据，当来源接进来 |
| 核验、留痕、署名责任 | AI 产出越多，人越核不过来；期刊、学校开始要求披露 | **升值层，主攻** |
| 本地数据、合规、模型中立 | 伦理 / 涉密 / 数据出境限制；学校可能指定国产或私有化模型 | 长期优势，守住 |

### 1.2 内部底子：已经有的比想象中多

| 支柱 | 已经有的 | 缺口 |
|---|---|---|
| **核验** | `bib-check`（引用闭环、外部元数据、更正 / 撤稿状态）、`lit_records.py`（Crossref 为准补题录）、`stats-check`、评审页「基础检查」与扫描提醒、**逐条裁决**（[待核实]、疑似编造的引用）、复现面板（按脚本实际执行）、评审冻结与三向判定、9 月试跑的 8 类故障注入 | 结果散在各步技能写的报告里，没有统一对象；检查由干活的同一个 Agent 自己跑；正文数字 → 分析输出、图 → 脚本的追溯没有贯通 |
| **留痕** | `acceptance-log.jsonl`（科研验收决定，append-only）、`artifacts.yaml` 提货单、`context.json`（实际下发的上下文）、`runId` 贯穿、接力链、用量与连接来源、AI 使用声明（AI 起草、人核对） | 记录分在项目文件和 Mesa 本机数据库两处（Run 在本机库里，换电脑就没了）；没有给导师、期刊、学位办看的成品视图；AI 使用声明靠 AI 回忆，不是从记录生成 |
| **记忆** | `.ccode/memory.md`（只记人确认的项目知识，状态机 + 依据）、`notes/index.json`、积累台账 `reading-list`、雷达跨轮记忆 | 只在单个项目里；换个项目，Agent 又从零认识这个人 |
| **课题组** | 无（Backlog「团队协作 2.0」） | — |
| **机构** | 任意 OpenAI / Anthropic 兼容端点、本地端点无密钥、国产模型预设、密钥不出本机 | 没有管理员策略、审计导出、离线安装 |

### 1.3 自身约束

- **0.1.1 是首个正式版**，还没有外部真实用户；macOS 签名公证、国内更新镜像还差账号与配置。
- **小团队**：九家 CLI × 两个平台的适配与金丝雀维护，是固定的大头开销。
- **无账号、无云**：这是信任来源，也限制了协作和数据回收。
- 9 月试跑定下的边界继续有效：**不做自动语义裁判、不做质量仪表盘、不做自动路由、不做全学科模板扩张**；脚本通过不等于论文可靠。

## 2. 定位调整

| | 现在 | 调整后 |
|---|---|---|
| 对外一句话 | AI 科研工作台：AI 干活，Mesa 管活，人拍板 | 不变，但重心从「管活」移到「**核活、记活**」 |
| 用户为什么来 | 一个界面用齐各家 Agent，流程带着走 | 用哪家都行，**出来的东西我敢交给导师和期刊** |

**北极星指标**（不靠遥测，见 §7）：一个用户在一个真实课题里，**被人签字采纳的 AI 产出有多少**，以及**核验在交出去之前拦下了多少问题**。

## 3. 四根支柱

每根支柱按「用户看到什么 → 复用什么 → 新增什么 → 边界 → 怎样算做成」写。

### 3.1 核验层：谁干的活都行，Mesa 帮你核（主攻）

**用户看到什么**

- 评审页「基础检查」那一行展开是一张**核验清单**：每条写清查了什么、结果、证据在哪，点一下跳到稿件对应位置和来源原文。
- 三种结果，颜色和文案固定：**通过**（机器能确定的事实，如 DOI 存在、哈希一致）/ **拦下**（机器确定有问题，如引用键指向另一篇、撤稿）/ **待你判断**（需要读懂内容的，如「这篇文献是否支持这句话」）。
- **待你判断**的条目直接汇入现有「逐条裁决」，不新开入口。
- 有第二家 Agent 可用时，评审页多一个 **请另一家复核**：换一家模型读原文找疑点，只给「疑点 + 原文摘录」，不给通过结论。

**复用什么**：`bib-check` 与 `lit_records.py` 的检查逻辑、逐条裁决、复现面板、评审冻结、`runId`、连接与绑定体系（复核用哪家走现有解析塔）。

**新增什么**

1. **统一的核验项**：每条检查写成同一种记录，落在项目里：
   `.ccode/checks/<runId>.jsonl`，一行一条：
   `{ id, kind, target(文件 + 位置), evidence(来源 / 哈希 / 原文摘录), status(passed|blocked|needs_human), checker(script:<名>|agent:<agent>/<model>), at }`。
   技能脚本改为输出这种格式；评审页只读这一个来源。
2. **按可确定程度分两类检查器**：
   - **脚本检查（确定性的）**：DOI / PMID 是否存在、题录是否与 Crossref 一致、更正 / 撤稿、引用键与来源一一对应、全文状态（全文 / 仅摘要）、来源哈希是否变了、数据文件哈希、复现输出与参考值的容差。
   - **引文段落核对（一期，专门对付幻觉）**：每处引用，干活的 Agent 都要给出支撑它的原文摘录和页码；脚本再到该文献的全文里逐字查找这段摘录（忽略换行和连字符断词）。找不到就拦下，说明这段摘录是编出来的；只有摘要的文献标「仅摘要」，不算核过。脚本只证明「原文里确实有这段话」；这段话是否真的支持论断，交给下面的 Agent 检查。
   - **统计自洽（二期）**：照 statcheck 的思路，从正文里抽出检验统计量和自由度（t、F、χ²、r、z），重算 p 值，与正文写的 p 值比对；再查效应量、置信区间、样本量三者是否对得上。只拦算术上的不一致，不评判方法选得好不好。
   - **Agent 检查（需要读懂的）**：论断与来源是否相符、统计方法与数据是否匹配。结果一律是 `needs_human`，**永远不自动通过**。这一条守住「不做自动语义裁判」。
3. **数字与图的追溯**（二期）：分析类步骤约定把要进正文的数值写进 `results/*.json`（带名字），正文用名字引用；脚本检查正文里的数和结果文件是否一致。图同理：每张图在提货单里登记生成脚本，复现时重跑比对。
4. **跨厂商复核**（二期）：复核默认选「与干活的不是同一家」的连接；复核只读、不写稿件，结果写成核验项。

**边界**

- 核验只给证据，不打总分，不出「质量分」或仪表盘。
- 「通过」只用于机器能确定的事实；凡要理解内容的，最多到「待你判断」。
- 文案上永远分开说：**文件已保存进项目 ≠ 核验通过 ≠ 你接受了科学结论**（沿用现有「保存到项目只表示文件进了课题」的口径）。

**怎样算做成**：试点用户的真实稿件里，核验在交给导师或期刊之前拦下过真实问题（编造引用、撤稿文献、数字对不上），并且用户说得出「这条是 Mesa 帮我发现的」。

### 3.2 研究记录：一份交得出去的过程档案

**用户看到什么**

- 项目页有一处 **研究记录**：按时间线列出每一步
  - **问了什么**：目标与任务书原文，取自 `context.json` 冻结的下发内容；
  - **用了哪些来源**：文献、数据文件，带哈希；
  - **谁做的**：哪家 Agent、哪个模型；
  - **核验结果**；
  - **人批准了哪一版**，在什么时候；
  - **改过什么**：特别列出「科学改动」，即数字、因果、样本、结论范围的变化；
  - **人亲手做的**：人写或改的段落、人的逐条裁决和审查意见、人否掉的方案。
- 三个导出按钮，都是本机生成文件：
  1. **AI 使用声明草稿**：从记录里**统计**出来（哪些步骤用了哪家模型做什么），不靠 AI 回忆；人核对后定稿，接进现有投稿材料步骤。
  2. **复现包**：脚本、数据哈希、运行命令、环境说明、图的生成方式，打成一个文件夹或压缩包；数据本体可选带不带。
  3. **过程报告（给导师、学位办、伦理审查）**：一份可读的 HTML 或 PDF，内容是关键决定、人工批准、核验摘要，以及一节**人机分工**：哪些部分是人写的、人改了什么、人做了哪些判断，哪些部分由 AI 起草并经人核对。国内学校在查 AIGC，这份记录本身就能说明人的贡献。默认不带对话原文，勾选才带，带也要先脱敏。
- **为什么能留住人**：用上两年，研究记录就是这个人的研究档案，换工具就等于丢了档案。格式必须开放（JSONL 加 Markdown，任何工具都读得了），用户才信得过；最好用的读写工具是 Mesa。

**复用什么**：`acceptance-log.jsonl`、`artifacts.yaml`、`context.json`、`runId`、接力链、用量与连接来源、出站脱敏（`redact_sensitive_text`）、现有 AI 使用声明的人工核对流程。

**新增什么**

1. **记录落在项目里**：把 Run 的关键事实（agent、连接、模型、开始结束、结果）在 Run 结束时追加到项目内的 `.ccode/record.jsonl`。原因是 Run 现在只在本机数据库里，换电脑、给导师拷项目时记录就断了。数据库仍是索引，项目文件才是权威记录。
   `record.jsonl` 与 `.ccode/checks/` 按 `acceptance-log.jsonl` 的现行口径处理：append-only、进 `.gitignore`、列入合并闸门的台账豁免（`review_contract::is_untracked_ledger_file`），不影响工作区合并。
   代价是：拷整个项目文件夹时记录会跟着走，通过 git 克隆则不会。课题组阶段如果需要记录随 git 走，到时候再议。
2. **研究记录视图**：只读汇总上面这些文件，不新造第二套状态。
3. 三个导出器。

**边界**

- 记录是**透明说明**，不是规避 AIGC 检测的工具：不做「降 AI 率」，不改写文字掩盖 AI 痕迹，宣传里也不这么说。
- 密钥、连接端点不进任何导出；对话原文默认不导出。
- 不做云端存证、区块链一类的东西；文件归用户，用户自己决定交给谁。

**怎样算做成**：试点里至少一位用户把过程报告或 AI 使用声明真的交给了导师或期刊，并且对方能看懂。

### 3.3 研究档案：越用越懂你（跨项目记忆）

**用户看到什么**

- 设置里有一份 **我的研究档案**，按块列出：研究方向与常用关键词、读过的文献总表与精读笔记（跨项目去重）、做过的判断、常用方法、数据处理习惯（例如缺失值怎么处理、异常值剔除口径）、写作偏好、导师反复提过的意见、试过并放弃的方向。跨项目、跨年份积累。
- 新开一个项目或一步时，Agent 自动知道这些，比如「这篇你在 2026 年的 X 项目精读过，笔记在这里」「你的导师不喜欢在摘要里写 novel」。
- 每条都能看、改、作废、删除。

**复用什么**：`.ccode/memory.md` 的规则原样升到用户层：**只记人确认过的内容**，带依据，有 active / superseded / revoked 状态，Agent 只能提议。文献总表从各项目的 `included.json`、`notes/index.json` 汇总，按 DOI 去重。

**新增什么**

1. 用户层档案目录（内部路径按现有身份放在 `~/ccode/` 下，不随展示名改）。
2. **提议来源**：审查报告里被反复拒绝的同类意见、逐条裁决里人写的理由、项目知识里标了「适用于所有项目」的条目，攒够了由 Mesa 提议进档案，人点了才进。
3. 上下文包加一段「研究档案摘要」，有预算上限，可在项目里关掉。

**边界**

- 只在本机，格式是开放的 Markdown / JSON，用户随时能整份带走或删掉。
- 不做向量库、不建「知识图谱」；先用简单的汇总加检索，够用为止。
- 不从对话里自动抽取「事实」写进档案。

**怎样算做成**：试点用户开第二个项目时，明确感觉到 Agent「认识我」，并且没有出现档案内容被 Agent 当成事实乱用的情况。

### 3.4 课题组：留住一个人，不如留住一个组（试点后再定）

**为什么**：科研的真实单位是课题组。导师审学生的产出，组里共享文献和方法，师兄师姐毕业后经验不流失。一个组用开了，个人很难离开；付钱的也是导师和学校。

**最小形态（不建服务器、不做账号）**

- **组仓库**：组里自己的 git 远程（学校 GitLab、Gitee、校内服务器或任意 git 服务），放组规范（写作要求、模板、技能）、组文献总表、组内常用方法，以及**踩过的坑**（如某台仪器的数据要先校正、某期刊审稿人常挑什么）。经验条目沿用研究档案的规则：组员提议，导师或组长确认才进。师兄师姐毕业后，这些经验留在组里。Mesa 能「加入课题组」，就是登记这个仓库，定期拉取。
- **导师评审包**：学生从 3.2 导出一份评审包（稿件 + 研究记录 + 核验清单），通过任何渠道交给导师；导师在自己的 Mesa 里打开，逐条写意见；意见包传回学生的 Mesa，变成审查报告条目，走现有接受 / 拒绝 / 修改流程。

**边界**：不做实时协同编辑，不做在线账号体系，不托管用户数据。

**需要先拍板**：这一块碰到「团队协作」和 §11.5 的「无云」，要等试点证明导师端确实有需求再立项。

### 3.5 机构版：私有化与合规（有客户再做）

- **为什么是这个市场**：高校、研究所、医院要同时满足合规、私有化部署和多模型中立，海外大厂很难在国内机构里三者兼顾，这是小团队打得赢的地方。
- 预置校内自建模型的连接模板：GLM、Qwen、DeepSeek 自建部署，以及常见推理服务（vLLM、Ollama、其他兼容端点）；数据不出单位。
- **管理员策略文件**：锁定可用连接、禁止外网连接、强制开启研究记录。
- 审计导出（3.2 的机构版）、离线安装包。

**触发条件**：有一个明确的高校、研究所或医院客户愿意试点。在那之前只保证「任意兼容端点 + 本地无密钥」能顺畅用，不做管理端。

## 4. 主动收缩：把力气从贬值层挪出来

### 4.1 CLI 支持分级（需拍板，和「九家全部支持」有冲突）

| 级别 | 范围（建议） | 承诺 |
|---|---|---|
| 一等 | Claude Code、Codex，加一家国产（按试点用户实际用量定，候选 Kimi / Qwen） | 新功能先在这几家做全：聊天层旁路、核验复核、全局写入 |
| 维护级 | 其余六家 | 能启动、能注入连接、能看会话、金丝雀不红；新功能尽力而为，做不到就在界面上写明 |

不删任何一家，只是不再让九家同步拖慢每一个新功能。

### 4.2 从「步骤」转向「检查点」

- 现有六套模板保留，但新设计都以**人在哪里签字、签之前要看到什么核验**为中心，而不是拆成更多步骤。
- 长期目标：用户只定「要交付什么 + 在哪些地方要我签字」，中间怎么做交给 Agent，Mesa 保证每个签字点都带着核验清单和记录。
- 这不违反「禁止自动拆任务」：拆不拆是 Agent 自己的事，Mesa 不编排，只守签字点。

### 4.3 继续把技术细节藏起来

科研用户不该看见 git、worktree、分支、终端。现有白话双层继续推进；新功能的界面文字一律不出现这些词，必须出现时给白话说法。

### 4.4 流程减负（2026-11-02 加）

- **任务书瘦身**：核验一期上线时，把任务书里由脚本接手的叮嘱（引用键、DOI、撤稿、原句出处一类）删掉，只留目标、产物、边界，靠核验兜底。
- **签字点收拢**：评审、逐条裁决、审查报告、验收决定收成每步一个签字的地方；改界面面广，等试点用过一轮再动。
- **步骤可合并**：检查点固定，中间步骤允许合并；试点之后按反馈定。至少在试点结果出来前不新增模板与步骤。

## 5. 路线图

以 2026-11 为起点；科研用户的高峰是**毕业论文季（3–5 月）**和**投稿返修**，路线按这个倒排。

| 阶段 | 时间（建议） | 做什么 | 进入下一阶段的条件 |
|---|---|---|---|
| **0 发出去，找到人** | 11 月–12 月中 | 0.1.1 正式发布；办 Apple 开发者账号完成签名公证；国内更新镜像建桶；招 8–10 位试点用户（至少 3 个学科，含 2 位导师），每人在 Mesa 里做一个真实课题；每两周一次 30 分钟访谈 | 至少 5 人走完一个课题的一半以上；拿到「卡在哪、绕开了 Mesa 做什么、哪一步最省事」的一手记录 |
| **1 核验一期 + 声明** | 12 月–1 月 | 统一核验项（3.1 新增 1、2 的脚本部分，含引文段落核对）；评审页核验清单；逐条裁决接入；Run 事实落项目（3.2 新增 1）；AI 使用声明从记录生成 | 试点稿件里核验拦下过真实问题；声明草稿被用户实际使用 |
| **2 核验二期 + 记录导出** | 2 月–3 月初（赶在毕业季前） | 数字追溯、图重建核验、统计自洽、跨厂商复核；研究记录视图与三个导出 | 至少一位用户把过程报告交给导师或期刊 |
| **3 研究档案 + 组试点** | 3 月–6 月 | 研究档案一期；如阶段 0 有导师需求，挑 1–2 个组试最小课题组形态 | 用户开第二个项目时用上档案；导师端反馈是否值得做 |
| **4 机构版** | 有客户再定 | 3.5 | — |

**这期间不做**：新增流程模板、新的 CLI 适配（除非金丝雀要求）、界面大改版。

## 6. 继续不做

- 自研 Agent 循环、自建虚拟机集群、通用 Manus 式竞品
- 自动语义裁判、质量总分、质量仪表盘
- 自动拆任务、智能路由
- 自建文献数据库、接管个人文献库
- 代码插件系统；科研包（本轮暂缓）
- 账号体系与云同步（课题组阶段如需要，另行拍板）
- 任何形式的「降 AI 率」「规避检测」

## 7. 没有遥测怎么知道做得对不对

- **试点访谈是主要信号**，阶段 0 就建立固定节奏，问的是行为（「上周你在哪一步离开了 Mesa」），不问满意度。
- **本机统计、自愿发回**（需拍板）：Mesa 只在本机记几项计数，如保存进项目的次数、核验拦下的条数、导出次数，不记内容。用户在反馈弹层里点一下才附带发出去，默认不发。
- 现有反馈入口与诊断包继续用。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 核验做成了「看起来很严」，其实只查了格式，给人虚假安全感 | 每条核验写清查了什么、没查什么；「待你判断」不许被折叠成通过 |
| 试点招不到人，或用两天就不用了 | 阶段 0 本身就是验证；没人用就先查上手门槛，不急着做阶段 1 |
| 厂商推出自家「科研模式」 | 核验与记录对所有 Agent 都适用，厂商的科研模式也可以当成一种 Runtime 接进来，它干活、Mesa 核和记 |
| 维护负担吃掉新功能 | CLI 分级；新功能只承诺一等支持 |
| 研究档案里的内容被 Agent 当成事实乱用 | 只收人确认的条目；注入时标明「这是用户的偏好与历史，不是事实依据」 |
