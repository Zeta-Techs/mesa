# 官方账号出网线路（线路体检）整体设计

> 状态：2026-11-06 用户拍板「§11 全部按建议」，一期已落地（见 §8 一期落地说明）。起因：用户把官方账号的出口接到一条固定、干净的英国住宅线路，
> 在公司 / 家里两地来回实测一整天，暴露出「代理设了」和「真的从对的地方出去」之间差了好几层。

## 0. 结论

- Mesa 现在只确认**设了出网代理、本机端口在监听**。实际要用好官方账号，需要确认的是：**这家服务的请求真的出得去，出口在受支持地区，而且每次出口一致**。
- 新增「线路体检」：针对每家官方账号，**从这家服务自己的域名、经和启动时完全相同的代理环境**探测一次，得到四样东西：代理来源、能不能到、出口地区、首包延迟。判定只有三档：通过 / 拦下 / 待你判断。
- 体检结果出现在三个地方：设置「网络」的体检卡、官方账号**启动前的预检**、出问题时进**收件箱**（只在状态变化时出声）。修复只做 Mesa 自己能做的：改 Mesa 自己的设置、打开代理软件；别的软件和别的机器只给检查清单。
- 既有拍板不动：Mesa 不当代理客户端、不建本地反代、官方连不上不回落中转、出网代理只给官方账号。

## 1. 这次实证（2026-11-06）

| # | 现象 | 说明了什么 |
|---|---|---|
| 1 | 设置里出网代理是 `127.0.0.1:7888`，那个端口根本没程序在听，用户一直不知道 | 现有检查只在**启动官方账号的那一刻**弹提示，设置页本身看不出代理已经失效 |
| 2 | 本机代理端口活着，但它下一跳的机器（另一台电脑、上游代理）关了，官方账号照样连不上 | **端口活着 ≠ 线路通**，要真的访问一次服务才能确认 |
| 3 | 代理软件按规则分流，同一个代理端口下，Claude 从英国出去，其他网站从新加坡出去 | **出口地区取决于访问的域名**。只能用这家服务自己的域名来测，用 ipinfo 之类的中立网站测出来的出口可能不一样 |
| 4 | 代理软件把新加的节点自动塞进了另一个分组的第一位，大部分境外流量悄悄改走了这个节点；换了网络后才暴露出来 | 代理软件的配置会被它自己改动。所以要**看实际结果，不看配置** |
| 5 | 备用节点名字里带「AI」，查下来是甲骨文云的机房 IP；名字带「家宽」的才是真正的住宅 IP | 节点名字不可信。出口的**类型**（住宅还是机房）要查出口 IP 所属网络才知道 |
| 6 | 用户关心：同一个账号别在英国、美国、台湾之间来回换 | **出口要稳定**。换了地区要让用户知道 |
| 7 | 中间多了一层中转（异地互连走了伦敦中转服务器），首包延迟从 1 秒涨到 3 秒，功能上不报错 | 「慢」也要能定位到具体是哪一段，不能只看通不通 |
| 8 | 某个桌面客户端对话突然变慢，用户以为是代理的问题，实际是对话上下文到了 54 万 token（首字 30–176 秒），同一条线路上命令行只要 2 秒 | 要能分清**网络慢**和**对话太长导致的慢**，不然用户会去改代理，白折腾 |
| 9 | Mesa 从访达打开时会读登录 shell 的环境，其中的 `https_proxy` 会传给**所有**子进程，包括中转连接的启动 | 代理的**来源**要看得见：是 Mesa 设置给的，还是 shell 带进来的，或者是连接的附加环境变量 |
| 10 | 中转连接（国内网关）本来就该直连，走代理反而绕远 | 体检只针对官方账号；中转连接只做「代理来源」的提示 |

## 2. 现在已有的底子

- `settings.rs`：`outbound_proxy` 设置项；`official_outbound_env_from` 生成官方启动注入的环境变量；`official_proxy_down_from` 检测本机回环代理端口是否在听（远端代理不探测）；`detect_outbound_proxy_inner` 从系统代理、环境变量、常见端口里找候选代理。
- `pty.rs`：官方账号启动结果带 `proxy_down`，`TerminalPage` 用 toast 提示「出网代理没有在运行」。
- `conn-issue.ts`：认出各家 CLI 实录过的「连不上」报错形态，只对官方账号给出「去设置出网代理」。
- `shell_env.rs`：从登录 shell 带入 `https_proxy` / `HTTPS_PROXY`（有意为之，见 environment.md）。
- 收件箱已有 `update:` 这类分类，是「不阻断干活，但必须能看见」的先例。

## 3. 原则

1. **看结果，不看配置**：判定依据是这一次真实请求的结果（能不能到、出口地区、延迟），不去解析代理软件的配置。
2. **与启动同源**：体检请求用的代理环境，必须和官方启动时注入的环境逐字段一致（同一个 `official_outbound_env_from` 生成，再叠加连接的 `extra_env`）。不允许体检能通、启动却不通。
3. **用这家服务自己的域名**：Claude 测 `claude.ai`，Codex 测 `chatgpt.com`，以此类推（见 §4.2）。
4. **不带凭据，不碰账号**：体检只访问公开的、不需要登录的地址，不带密钥、Cookie 或 token。
5. **只对官方账号**：中转连接不做体检，不提示「去设代理」（沿用 10-29 拍板）。
6. **状态变化才出声**：后台复查结果和上次一样，就不提醒（沿用「少占注意力」）。
7. **修复只动 Mesa 自己的东西**：可以改 Mesa 的设置、打开代理软件的窗口。不写系统代理，不调用代理软件的接口，不改别的机器。

## 4. 统一模型：一次体检

### 4.1 链路分段

```
代理来源 ──▶ 代理活着 ──▶ 到得了服务 ──▶ 出口地区 ──▶（可选）出口类型 ──▶ 首包延迟
 Mesa 设置     本机端口      这家服务自己     服务端看到的      住宅 / 机房        和上次比
 / shell 带入  在监听        的公开地址       国家或地区
 / 连接附加
```

前一段失败，后面几段就不再测。结果中要标明是**哪一段**失败（对应实证 2、7）。

### 4.2 各家探测地址

| Agent（官方账号） | 探测地址 | 出口地区从哪里取 | 分级 |
|---|---|---|---|
| Claude Code | `https://claude.ai/cdn-cgi/trace` | `loc=`（Cloudflare 返回） | 一等 |
| Codex（ChatGPT 账号） | `https://chatgpt.com/cdn-cgi/trace` | `loc=` | 一等 |
| Kimi Code | 国内服务，不需要出网代理 | — | 一等（只检查「不应该走代理却走了」） |
| Gemini CLI | `https://generativelanguage.googleapis.com/` 能否到达 | 拿不到，「出口地区」一栏写「这家服务不返回」 | 维护级 |
| Cursor | `https://cursor.com/` 能否到达 | 同上 | 维护级 |
| Grok Build | `https://x.ai/cdn-cgi/trace`（实施前核实是否在 Cloudflare 后面） | `loc=` 或拿不到 | 维护级 |
| 其余 | 没有官方账号形态，不做 | — | — |

`cdn-cgi/trace` 是 Cloudflare 的公开诊断页，返回请求方 IP 和国家，不需要登录。探测地址表放在 `agent_specs.rs` 的能力表里，不在别处硬编码；CLI 金丝雀每天检查这些地址是否还能用。

### 4.3 判定三档

| 档 | 条件 |
|---|---|
| **通过** | 到得了，出口地区不在这家服务的不支持名单里，并且和上次出口地区一致 |
| **拦下** | 代理来源指向的本机端口没在听；到不了服务（超时、被拒、TLS 失败）；出口地区在不支持名单里（例如 Claude、ChatGPT 从中国大陆或香港出去） |
| **待你判断** | 出口地区和上次不一样；这家服务不返回出口地区；（查了出口类型时）出口是机房 IP；首包延迟比最近中位数慢 3 倍以上 |

不支持名单只列确定不支持的地区，写在共享数据文件里，实施时以各家官方页面为准逐条核对。没在名单里不代表一定支持，所以界面不写「支持」，只写「不在已知不支持名单里」。

### 4.4 出口记忆

- 每家官方账号记最近 20 次体检的「出口地区 + 出口 IP 的前缀（/24）+ 时间」，存在 Mesa 的配置目录，不进项目、不上传。
- 用途只有两个：判断「和上次不一样」，以及在体检卡上显示「最近 7 天都从英国出去」。
- 不记完整 IP，不记账号身份。

### 4.5 出口类型（可选）

只有用户在体检卡上点「查出口类型」时才查：把出口 IP 发给一个公开的 IP 归属查询服务，得到它所属的网络运营商，再对照一份常见云厂商网络的名单（甲骨文、AWS、谷歌云、Azure、阿里云、腾讯云、DigitalOcean、Vultr 等）判断是住宅还是机房。结果缓存 24 小时。默认不查，因为要把出口 IP 发给第三方（见 §11 拍板 2）。

## 5. 出现在哪里

### 5.1 设置 →「网络」：线路体检卡（放在「出网代理」那一行下面）

- 每家**配了官方账号**的 Agent 一行：状态点（通过 / 拦下 / 待你判断）· 出口地区 · 首包延迟 · 「最近 7 天都从 XX 出去」· 「重测」。
- 卡片顶部写清**代理来源**，例如：「Mesa 设置：http://127.0.0.1:7897（在运行）」或「没在 Mesa 里设，用的是登录 shell 带进来的 https_proxy」。
- 填写或修改出网代理后自动体检一次。实证 1 的情况会**立刻**显示红色，不用等到启动时。

### 5.2 官方账号启动前的预检

- 取最近 5 分钟内的体检结果，没有就当场测一次（最多 6 秒，超时按「待你判断」处理，不卡住启动）。
- **通过**：静默启动，用户看不到任何提示。
- **拦下**：启动弹层里内联显示一行原因，三个按钮：「修复后启动」（见 §6）、「仍然启动」、「换成中转连接」（这家有中转连接时才显示）。
- **待你判断**：照常启动，标签页顶部出现一条可以关掉的提示，例如「这次从美国出去，最近 7 天都是英国」。
- 取代现在的 `proxy_down` toast：同一件事只说一次。

### 5.3 收件箱：`network:` 分类

- Mesa 开着、并且有官方账号的会话正在运行时，每 5 分钟后台复查一次。只有状态**变化**时才写一条收件箱卡片，例如「Claude 的线路断了：到不了服务」，卡片上就有修复按钮；恢复后这条卡片自动消失，不另外发「已恢复」。
- 不发系统通知，不弹窗，不造顶部横幅（沿用 `update:` 的口径）。

### 5.4 「慢」的分辨（对应实证 8）

- 对话层已经知道每个会话的上下文 token 数。用户觉得慢、或者首字延迟明显变长时，在原有的「连接出问题」提示位置区分两种情况：
  - 线路体检的首包延迟正常，但这个对话上下文很大 → 「这个对话已经有 54 万 token，变慢多半是对话太长，新开一个对话会快」；
  - 首包延迟本身变长了 → 指向线路体检卡。
- 只给提示，不自动压缩或新开对话。

## 6. 修复动作

| 失败的环节 | Mesa 能做的 | Mesa 不做、只给说明的 |
|---|---|---|
| 设置里的代理端口没在听 | 「打开代理软件」：按端口找到正在监听的已知客户端（Clash Verge、v2rayN 等），或打开上次检测到的那个；「换成检测到的代理」：重新检测，用户点选后写入 | — |
| 没设出网代理，但检测到有在运行的代理 | 一键填入（用户点选才写，沿用现有口径） | — |
| 到不了服务（本机端口是通的） | 重测一次，排除偶发 | 「代理软件的上游节点或下一跳不通」，附检查清单：换节点、检查中转机器、检查上游代理 |
| 出口在不支持地区 | — | 「去代理软件把这家服务的流量换到受支持地区的节点」 |
| 出口地区变了 | 「这是我故意的，记为新的常用出口」 | — |
| 中转连接却带着 shell 带进来的代理 | 只做提示（见 §11 拍板 3） | — |

## 7. 明确不做

- 不内置代理、不建本地反代、不接管系统代理、不调用代理软件的控制接口去切节点（实证 4 说明代理软件的配置会被它自己改动，Mesa 再插一手会更乱）。
- 不评价、不推荐任何机场或节点服务商。
- 体检结果不拿来自动切换连接，也不在官方连不上时自动改走中转（沿用拍板）。
- 不测中转连接的出口。
- 不把「多台机器互连、经公司线路出口」这类组网写进说明书。那是用户自己的网络环境，Mesa 只负责把结果测准。

## 8. 分期

| 期 | 内容 | 涉及 |
|---|---|---|
| 一 | 体检核心（§4.1–4.3，一等 Agent）+ 设置页体检卡 + 启动前预检取代 `proxy_down` toast | 新增 `route_check.rs`；`agent_specs.rs` 加探测地址；`SettingsPage`；`TerminalPage` 启动弹层 |
| 二 | 出口记忆（§4.4）+ 收件箱 `network:` + 后台复查 | `inbox.ts` 分类；后台任务只在有官方会话运行时启动 |
| 三 | 出口类型（§4.5，经拍板）+ 「慢」的分辨（§5.4）+ 维护级 Agent 的探测地址 | 对话层 `conn-issue.ts`；用量数据里的上下文大小 |

### 一期落地说明（2026-11-06）

- 不支持地区名单只有 Rust 一侧用，放在 `agent_specs.rs` 的 `AI_UNSUPPORTED_REGIONS` 常量里，不另建共享数据文件。
- 启动预检被拦下时只有两个选择：**仍要启动** 和取消（取消后提示去 设置 → 网络 看原因）。「修复后启动」「换成中转连接」放到二期，和收件箱的修复按钮一起做。
- 「待你判断」一期用 toast 提示，不做标签页顶部的提示条。
- 代理是 SOCKS 时一期只确认端口在运行，结果记为「待你判断」（reqwest 没开 socks 特性，开了要 `npm run gen:notices`，留到需要时再做）。
- 实测（家里，规则分流代理）：经代理 claude.ai / chatgpt.com 都是 GB、约 1.5 秒；直连 claude.ai 返回 CN（会判拦下：地区不支持），chatgpt.com 超时（判拦下：连不上）；死端口判拦下：连接被拒。

### 二期落地说明（2026-11-06）

- 出口记忆、收件箱「线路」（`net:`）、后台复查、修复按钮（换成检测到的代理 / 打开代理软件）、启动预检「修复后启动」都已做。
- 「换成中转连接」没做：换连接会改变计费方式和模型，Mesa 不替你挑，换连接仍在启动栏里自己选。
- 收件箱条目只收「拦下」和「换了出口地区」；SOCKS 测不了、没拿到地区这类待你判断只在体检卡上显示，不进收件箱。

### 三期落地说明（2026-11-06）

- 用户要求文案简单：通过只写「英国 · 1.0 秒」，其余见 profiles.md「线路体检」三期条。
- 维护级补了 Grok（x.ai trace，有地区）、Gemini、Cursor（只测通不通，连得上即通过）；Qwen、Kimi、CodeBuddy 是国内服务、OpenCode 没有官方账号，不测。
- 出口类型：按钮触发，完整 IP 只在内存；分类靠所属网络名称与反解名，判不出说「看不出来」，不猜。
- 「慢」的分辨落在上下文圆环弹层（过 30 万 token 提示），没有放进连接出错提示：CLI 的首字延迟 Mesa 拿不到，只有上下文大小是确定的。

## 9. 实施前必须实测

- 在国内直连、规则分流代理、全局代理三种环境下，分别验证 §4.2 每个探测地址的返回（是否走 Cloudflare、`loc` 是否准确、不登录能否访问）。
- 验证体检请求与官方启动的代理环境逐字段一致：同一台机器上故意把代理指向一个不存在的端口、一个只对部分域名生效的代理，体检和实际启动的结果必须一致。
- 后台复查对电量和流量的影响：在 Mac 上跑 24 小时，看请求次数和总流量（预计每天约 300 次、一两 MB）。

## 10. 测试与验收

- Rust：判定函数是纯函数，输入是「各段结果 + 历史 + 不支持名单」，输出档位和原因，覆盖 §4.3 的每一条；代理来源判别（设置 / shell / 连接附加）单独测。
- 前端：体检卡三种状态的渲染、启动弹层三个按钮的行为，照 research-*-ui 测试的打包口径。
- 真机点验清单交给用户点：故意关掉代理软件、把代理软件的出口切到香港、切到另一个地区、拔掉下一跳，逐一看设置卡、启动预检、收件箱是否按预期出现，以及会不会重复提醒。

## 11. 需要你拍板

1. **启动前预检遇到「拦下」时，是挡在弹层里让你选，还是只提示、照常启动？** 建议挡在弹层里：实证里官方账号走错出口的代价（被风控）比多点一下大。
2. **出口类型（住宅 / 机房）要不要查？** 查的话要把出口 IP 发给第三方查询服务。建议做成按钮，默认不查。
3. **中转连接继承了登录 shell 里的代理变量（实证 9），要不要在中转启动时去掉？** 用规则分流的代理时，留着也没坏处（国内网关会直连）；用全局代理时，中转会被绕到境外变慢。建议先只在体检卡上**显示**「中转连接也会带上 shell 里的代理」，不改行为，等有人报慢再定。
4. **Mesa 里新开的普通终端标签要不要也带上出网代理？** 用户在 Mesa 的普通终端里手动敲 `claude`，现在用的是 shell 自己的环境。建议不带，保持「出网代理只给官方启动」的口径。
5. **后台复查的频率和条件**：建议只在有官方会话正在运行时每 5 分钟一次；Mesa 开着但没在用官方账号时不复查。
