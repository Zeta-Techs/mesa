## 0. 一句话

一个课题组反复做的那件事——「我们组的单细胞数据质控」「本领域的 Meta 分析数据提取」「导师要的周报格式」——今天要在流程编辑器、技能页、
定时任务页三处分别配，配好了也带不走、分享不了。**任务包把一件专属科研任务打成一件东西：声明 + 文字 + 可选脚本，不含跑在 Mesa 里的代码。**
用户能自己写（跟 AI 一起写）、能试跑、能装进自己的库反复用、能导出给别人；Mesa 的不变量一条也改不动。

## 1. 参考：DeepSeek 原型的「一切皆插件」学什么

依据 `deepseek-ai/dsh-superagent-prototype` 的 `docs/000`–`008`（文章原文本机抓不到）。原型建在一个插件框架上，GitHub / 飞书两种事件来源
都是插件，和用户新写的走同一套接口。学的是四个做法，不是「能装插件」本身：

| DeepSeek 原型 | 在 Mesa 里怎么用 |
|---|---|
| **窄契约**：一种来源只实现翻译事件、声明配置、回复、健康检查几样（008 Cookbook） | 任务包只声明一组固定字段（§3），Mesa 的执行、隔离、评审、核验全部复用，包不碰 |
| **种类与实例分开**：Source kind 是可复用实现，instance 是一份配置 | 任务包是种类，项目里的某一步是实例：同一个包在不同项目里填不同参数 |
| **声明字段即生成表单**：`fields` 生成设置表单，不写界面代码 | 包声明参数，开工弹层与流程编辑器自动出表单（§3.2） |
| **能用文字描述的行为写成提示词，不做成设置**（000 Philosophy） | 「怎么做」写在技能与简报里；Mesa 不为某个学科加开关 |
| **覆盖内置要记基于哪一版**，内置升级标「默认内容已更新」并排看差异（004 Prompts） | 内置步骤可「另存为我的版本」；内置升级时提示差异，人选保留还是用新版（§6） |
| **分层不可越级**：代码强制的事实 > 内置文字 > 规则 > 团队文字 > 外部文本 | 包改不动 Mesa 的不变量（§4） |
| **健康检查** + 按角色的提示词长度预算测试（`model-surface.spec`） | 安装和开工前体检；任务书长度预算照现有测试口径（§5） |

不学的：原型的插件是跑在宿主进程里的 TypeScript 代码。Mesa 继续不做代码插件（§9 第 2 项）。

## 2. 现在站在哪

### 2.1 已有的底子

| 零件 | 现状 | 位置 |
|---|---|---|
| 步骤合同 | `brief`、`inputs` / `optionalInputs` / `anyOfInputs`、`expectedArtifacts`、`acceptanceCriteria`、`humanTasks`、`decisions`、`decisionMode`、`skills` / `requiredSkills`、`run`、`resources`、`discussionSeeds`、`role` | `ProjectStepDto`（types.ts）、project.toml |
| 用户模板 | 项目页「另存为模板」，存整条流程的 steps，不带技能 | 配置目录 `ccode/pipeline-templates.json`，`list/save/delete_pipeline_template` |
| 技能库与技能位 | 新建、导入、适配到流水线、合成新技能；`provides` 顶替内置位；简报用 `{skill:锚名}` | 配置目录 `ccode/skills/` + `skills.json`；pipeline.md「技能位与个性化替换」 |
| AI 起草、人确认落库 | 「新建巡检技能」：草稿写进 `.ccode/drafts/`，人确认才入库 | scheduler.rs `start_watch_skill_draft` |
| 核验插口 | 任何检查器写 `.ccode/checks/<名字>.jsonl` 就进评审页；不在内置五个脚本里的，判「通过」自动降成「待你判断」 | research_record.rs `SCRIPT_CHECK_FILES` |
| 触发 | 定时任务、事件规则（目录 / 雷达 / 手机，默认只记录） | scheduler.rs |
| 新增步骤的人工检查清单 | 七条硬规则 + 检查清单 | step-panel.md §一、§四 |
| 任务书长度预算 | 每套模板有上限，超了测试红 | tests/research-usability.test.ts |

### 2.2 缺什么

- 没有一个「单位」把一件任务的流程合同、技能、参数、核验、触发打在一起：要分三处配，配好了带不走。
- 用户模板只存 steps，不带它依赖的技能，换一台电脑就缺技能。
- 没有参数：同一个任务换个期刊、换个显著性水平，只能改简报原文。
- 改了内置步骤后，内置再升级就没法知道差了什么。
- 「新增步骤检查清单」只给人看，没有机器校验，用户自己写的步骤没人把关。

### 2.3 会碰到的既有拍板

- **科研包（学科包分发）暂缓**（2026-11-02，design-research-moat §6）：§9 第 1 项要部分解禁。
- **不做代码插件系统**（architecture §11 MVP 起；design-research-moat §6）：本稿坚持，包里没有在 Mesa 进程里运行的代码。
- **替换必须人显式、不按特征自动推荐**（2026-09-07 / 10-11）：包只由人挑、人装、人挂。
- **换技能不换验收**（2026-10-11）：包里的验收与技能身份解耦，沿用。
- **Agent 的判断永不自动通过**（2026-11-02）：包里的核验脚本同口径（§9 第 3 项）。
- **步骤面板七条硬规则**（step-panel.md）：包的步骤必须过它，第二期起由机器校验。

## 3. 任务包长什么样

### 3.1 目录

```
<配置目录>/ccode/packs/<包 id>/
  pack.toml        身份 + 参数 + 步骤合同 + 可选触发（下表）
  skills/<名>/     随包的技能（SKILL.md 及其 scripts/），装包时进技能库，标来源「包：<名>」
  checks/<名>.py   可选：核验脚本，结果写 .ccode/checks/<包 id>-<名>.jsonl
  README.md        给人看的说明：解决什么、怎么用、产出什么
```

### 3.2 pack.toml 字段（闭集）

| 段 | 字段 | 说明 |
|---|---|---|
| 身份 | `id`、`name`、`version`、`description`、`author`、`based_on`（覆盖内置时记基于哪个内置、哪一版） | `id` 走 `paths::sanitize_fs_name` |
| 参数 | `[[params]]`：`key`、`label`、`type`（text / select / number / bool / path / file）、`default`、`options`、`help`、`required` | 生成表单；值存在 project.toml 该步的 `params`，任务书里 `{param:key}` 替换；`path` 只能是项目内相对路径 |
| 步骤合同 | `[[steps]]`：与 `ProjectStepDto` 同名同义的字段，`brief` 可用 `{param:key}` 与 `{skill:锚名}` | 一个包可以是一步，也可以是一小段流程（几步） |
| 必问 | `extra_must_ask`：在七类之外加的必问事项（如「换细胞类型注释参考库」） | 只能加，不能减七类 |
| 依赖 | `requires`：Python 包、R 包、命令（quarto / latexmk）、最低 CLI 能力（无头写盘、读 PDF） | 体检用，不自动装 |
| 触发（可选） | `[trigger]`：`schedule`（周期）或 `event`（目录 / 雷达 / 手机，模式缺省只记录） | 装进项目时生成定时任务或事件规则，仍走现有规则 |
| 核验（可选） | `[[checks]]`：`name`、`script`、`when`（收尾 / 评审前） | 见 §3.4 |

### 3.3 一件任务的三种用法

- **流程里的一步或一段**：流程编辑器「＋ 从我的任务添加」，按参数表单填值，插进流程。
- **一次性目标**（工作项目、不用流程的科研项目）：「记下目标」时选一个我的任务当模板。
- **定时 / 事件**：带 `[trigger]` 的包装进项目时，顺带建定时任务或事件规则（事件规则照旧默认只记录）。

### 3.4 核验脚本怎么接

- 脚本由 Agent 在隔离副本里按任务书要求运行，或由评审前的检查步骤运行；产出写进 `.ccode/checks/<包 id>-<名>.jsonl`，格式与现有核验项完全一致。
- 不在内置五个脚本里，所以「通过」一律降为「待你判断」，「拦下」照常进逐条裁决（§9 第 3 项）。
- 包不能写内置五个文件名（`cite-refs.jsonl` 等），装包时校验，冒名拒装。

## 4. 包改不动的东西（Mesa 的不变量）

参照 DeepSeek「代码强制的事实最高，提示词改不动」：

- 隔离副本、评审才进项目、采纳只经现有入口；保护路径。
- 七类必问（只能加）；步骤暂停策略的语义。
- 核验三档；「通过」只认内置脚本；不打总分。
- 密钥不进 shell、不进任务书、不进包；包里出现疑似密钥拒装（复用 Rust 层脱敏的识别）。
- 任务书长度预算；路径方言与文件名规则；Python 一律走 `usable_python`、Windows 提示改用 `python`。
- 研究记录、AI 使用记录照常记，包不能关。
- 流程正典产物的固定口径（如 lit-search 七项产物、quarto 输出目录）：包的步骤占用内置技能位时，这些口径照旧适用。

## 5. 机器校验（第二期起，装包与保存时跑）

把 step-panel.md「新增模板 / 新增步骤检查清单」与七条硬规则里能机器判的做成校验器，结果分「拦下 / 提醒」两档，**提醒不拦**：

- 拦下：字段不在闭集；`{param:}` 引用了没声明的参数；`{skill:}` 锚名不在闭集；路径越出项目或写 `.git` / `.ccode`；
  冒用内置核验文件名；包含疑似密钥；任务书拼出来超过长度预算；必问减了七类。
- 提醒：预期产物只写了目录通配（应先写能证明完成的入口文件）；第二步起的必需输入没有上游产物覆盖；简报里有「问用户」但没声明决策项；
  没有任何验收条件；依赖里有的命令本机没装。

## 6. 内置也是包（第四期）

- 六套内置模板改成同一种包格式随应用分发（DeepSeek：内置来源和用户来源走同一接口），`pipeline-presets.ts` 的简报文字迁成包文件，
  现有的模板长度预算测试改读包文件。
- 任何内置步骤可以「另存为我的版本」：复制成我的包，`based_on` 记内置包 id 与版本。
- 内置升级、而我的版本基于旧版时，「我的任务」里标「内置有更新」，并排看内置旧版 → 新版的差异与我的改动，人选「保留我的」「用新版」或「手动合并」；
  没改过的内置自动跟新版。
- 迁移：现有用户模板（`pipeline-templates.json`）一次性转成包（只有 steps、没有技能与参数），转完旧文件改名留底；按「未发布不养闲机器」不留两套。

## 7. 用户怎么建、怎么分享

### 7.1 建

1. **另存**（第一期）：项目页流程里选一步或连续几步「另存为我的任务」，带上它们挂的用户技能；简报里的具体值（期刊名、阈值）
   可在弹层里点选「改成参数」。
2. **跟 AI 写**（第二期）：「＋ 新建我的任务」→ 用几句话描述，可附组里的 SOP、一篇方法学论文、一份样例数据 →
   AI 按内置作者技能（`task-pack-author`，带 §3 字段说明与 §5 检查清单）在草稿目录写出整个包 → Mesa 校验 →
   预览成真实的步骤卡与任务书 → **在示例项目副本上试跑一遍**（「动真实数据先干跑」）→ 人点「装进我的任务」。
3. **手改**：「我的任务」里每个包可以打开 pack.toml 与技能编辑，保存时过校验，留历史版本。

### 7.2 分享

- 导出成一个 zip（包目录原样）。
- 导入时先只读解开，列出：会装哪些技能（与库里同名的怎么处理）、带哪些脚本（逐个可看全文）、需要哪些依赖、参数有哪些；
  人确认才装。来自别人的脚本首次运行前再提示一次。
- 不做公开分发、市场、在线目录（§9 第 1 项）。

## 10. 验收

- 第一期：在一个真实项目副本上，把调顺的一步「另存为我的任务」，把期刊名改成参数；换一个新项目「从我的任务添加」，填另一个期刊，
  开工后任务书里参数已替换、技能已就位，跑完照常评审。
- 第二期：用三段不同领域的 SOP 让 AI 各写一个包，校验器拦下故意写错的字段与超预算任务书；试跑通过后装库可用。
- 第三期：包内核验脚本产出的条目出现在评审页，「通过」显示为待你判断，「拦下」进逐条裁决。
- 第四期：导出的 zip 在另一台机器导入后能直接用；内置升级时我的版本能看到差异并三选一。
