## 1. 现状与问题

连接编辑弹层对九家是**同一张表单**：网关（地址、密钥）→ 模型名单（第一个是默认）→ 模型分工（Claude / Grok / OpenCode 才有）→ 同时绑到 → 名称。
各家差异藏在三处，用户看不见或看不全：

| 问题 | 现在的样子 | 后果 |
|---|---|---|
| Claude 的四个别名靠**名单顺序**隐式占位 | 名单第 1–4 个依次占 sonnet / opus / haiku / fable，只读「Claude 别名指向」默认收起 | 想让 opus 指向某个模型，只能拖名单顺序；想让 haiku 用便宜模型，要去「模型分工」另选；两处配合才能凑出截图那张表 |
| 每个模型的能力（上下文、思考、视觉）在**网关库** | 网关库模型行展开尾部「能力声明」 | 设 Claude 用 1M 上下文要离开连接弹层去网关库，且不知道这一项和 Claude 有关 |
| 各家特有的东西散在别处或没有入口 | Gemini 认证方式只在聊天卡上出；Grok API 后端在绑定字段；Kimi / Qwen 协议是一个下拉；Codex 思考档、Cursor「只能 Mesa 内用」没处说 | 每家「怎么才算配对了」要靠说明书和报错 |

## 2. 结论：一个骨架 + 每家一块「这家怎么用」，不做九个页面

**不照搬 cc-switch 的「每家一套表单」**。理由：
- Mesa 的对象模型是「网关 × 绑定」（profiles.md §2）：地址、密钥、每个模型的能力与策略属于网关，一个网关同时绑给好几家；九套表单会把这些共享字段拆成九份，回到 cc-switch「同一把密钥每家各填一遍」的老路。
- 九家真正不同的只有「这家拿这些模型干什么」：别名槽、后台小模型、协议、思考档写法、认证方式。这部分适合**按规格渲染**，不适合手写九个页面。

```
┌ 编辑连接 · Claude Code ───────────────────────────────────────┐
│ 网关      [GLM 中转 ▾]  地址 https://…  密钥 ••••3f2a   打开网关库 │  ← 九家同一套
│ 模型      ☑ glm-5.3  ☑ glm-5.3-flash  ☑ kimi-k3   [刷新目录]      │  ← 九家同一套（勾选，不再靠顺序表达别名）
│ ─ Claude Code 怎么用这些模型 ───────────────────────────────── │  ← 这一块按 Agent 换
│  角色        实际请求模型        /model 显示名        上下文      │
│  默认（主）  [glm-5.3     ▾]    GLM · glm-5.3         200K       │
│  Sonnet      [glm-5.3     ▾]    （同上，可改）         200K       │
│  Opus        [kimi-k3     ▾]                          1M ✓已声明  │
│  Haiku       [glm-5.3-flash▾]   后台小任务也用它        128K       │
│  Fable       [跟默认      ▾]                                      │
│  子 Agent    [跟默认      ▾]    不显示在 /model 菜单               │
│  [一键：全部用默认]                                               │
│ ─ 生效预览 ──────────────────────────────────────────────────── │  ← 九家同一套，内容按 Agent
│  在 Mesa 里启动：…（注入了什么）  设为全局后外面直接用：…（写哪个文件哪些键）│
│  外部可能被盖掉：你的 shell 导出了 …                               │
│ 同时绑到 …     名称 …                                  [取消][保存] │
└──────────────────────────────────────────────────────────────┘
```

## 3. 每家「怎么用这些模型」一块放什么

| Agent | 这一块的内容 | 数据落在哪（不新增存储的尽量复用） |
|---|---|---|
| Claude Code | 别名映射表（默认 / Sonnet / Opus / Haiku / Fable / 子 Agent → 名单里的模型或「跟默认」）、可改的 /model 显示名、上下文列（读能力库，点开就地改「能力声明」）、思考档 | 新绑定字段 `claude_slots`（槽 → 模型，空 = 跟默认）取代「名单顺序占槽」；`role_models.small` 并进 Haiku 行、`subagent` 并进子 Agent 行；上下文写现有能力覆盖层（全局按模型，所有 Agent 共用，界面写明） |
| Codex | 选择器里列哪些模型（名单即 catalog）、默认模型、思考档；Responses 端点检查结果；「客户端要重启」 | 现有字段 |
| Gemini | 认证方式状态（不是「API Key」时直接给「设成 API Key」按钮，同聊天卡）；模型进 /model 选择器要重启；温度 / top_p / 输出上限（只设为全局生效） | 现有字段 + `gemini_use_api_key_auth` |
| Qwen | 协议（OpenAI / Anthropic）、每模型思考档与上下文（只设为全局生效）；官方登录已停用的说明 | 现有字段 |
| OpenCode | 后台小模型；每模型温度 / 思考档 | 现有 `role_models.small` |
| Kimi | 协议（kimi / openai / anthropic），思考档只在 kimi 协议显示；上下文（Kimi 必填，未知时写的是保守下限，提示去声明） | 现有字段 |
| CodeBuddy | 地址用的是网关的 OpenAI 地址（说明）；名单写进 models.json；不支持思考档的说明 | 现有字段 |
| Grok | 后台小模型、API 后端（responses / chat_completions / messages）、思考档菜单 | 现有 `role_models.small`、`api_backend` |
| Cursor | 只有一句：「Cursor 只能在 Mesa 里启动时带上这条连接，不能设为全局」 | 无 |

渲染规则：这块的**结构由后端规格给**（`agent_specs.rs` 每家一张「连接表单规格」：有哪些角色行、哪些字段、每项只在启动生效 / 只在设为全局生效 / 都生效），
经 `agent_capabilities` 下发；前端按规格画，不在前端写「如果是 Claude 就……」。说明文字同样来自规格，保证与写盘、注入同源。

## 4. 生效预览：让「对不对」看得见

弹层底部常驻一块「生效预览」，按当前表单实时算（不保存也能看），两栏：
- **在 Mesa 里启动**：调现有启动预览（`preview_launch_plan`，密钥脱敏）——注入的环境变量 / 参数 / 覆盖层。
- **设为全局后外面直接用**：调 `preview_profile_global`——写哪个文件、哪些键，和 `skippedPolicies`、`overrideNotes`。

截图那种表回答的是「我想怎么配」，生效预览回答的是「CLI 实际会拿到什么」。两者放在一起，配错当场能看出来，不用等启动报错。

## 5. 以后怎么保持每一家都正确（四层，前两层已有）

| 层 | 管什么 | 状态 |
|---|---|---|
| ① 写盘 / 注入的单一来源 | 每家的写法只在 `global_config.rs` / `agents.rs` 一处；通道表与写盘函数互锁（`policy_channel_table_agrees_with_patch_functions`）、黄金样本（`capability_golden`） | 已有；本方案把「表单规格」也收进 `agent_specs.rs`，再加一条测试：规格里每个字段都要有写盘或注入的去处，反之亦然 |
| ② 每天金丝雀 | 九家最新版：请求、旁路、会话、画面、**全局配置**（10-30 新增：Mesa 写进去的配置外部 CLI 还认不认） | 已有，红了按 `mesa-cli-canary` 技能处理 |
| ③ 应用里的体检 | 设为全局后复检、外部改过（漂移）提醒、会被盖掉的提醒、生效预览 | 前三项已有，生效预览本方案新增 |
| ④ 定期复核官方文档 | 金丝雀只能发现「行为变了」，发现不了「官方新增了更好的写法」（如 CodeBuddy `models.json`、Claude `effortLevel`） | 新增：每个 Mesa 版本发版前，按 `agent-integration-matrix.md` 逐家对一遍官方配置文档的更新日志，结论记 matrix 对应节（发版前检查项加一条） |

## 6. 待拍板

1. Claude 的别名改成**显式映射表**（新字段 `claude_slots`），不再靠名单顺序占槽？——推荐：是。顺序占槽是隐式规则，用户问过「为什么 opus 是这个」。存量绑定迁移：按现在的顺序规则算一遍写进新字段，用户看到的映射不变。
2. 上下文 / 1M 在映射表里**就地可改**，写的是全局「能力声明」（所有 Agent 共用这个模型的声明）？——推荐：是，界面写明「对所有 Agent 生效」。不做成 Claude 专属的勾选，免得同一个模型在 Claude 里 1M、在 Kimi 里 128K。
3. 显示名可改？——推荐：可改，留空用「连接名 · 模型」（现行）。只有 Claude Code / Gemini / Kimi / Grok / OpenCode 有显示名的地方，其余家不出这一列。
4. 生效预览常驻在弹层底部，还是折叠成一行「看实际会写什么」？——推荐：折叠，展开后两栏。
5. 节奏：先做 Claude Code（截图那张表 + 生效预览），其余八家的「怎么用」块第二批按规格补齐？——推荐：是。
