# Mesa 可靠投递与恢复

## 范围与取舍

2026-11-12 用户要求在 agent-autoloop 源码调研后设计并执行适用于 Mesa 的方案。
借鉴任务先落盘、回执幂等、结果不明不盲目重做；不接入第二套调度器，不改科研步骤、人写规则、授权、评审和采纳。

本批完成两条现有链路：事件批次领取/收尾/异常恢复，人工回答准备/领取/送达确认。
后续全阶段于 2026-11-12 经用户要求继续开发：独立后台、授权内分轮执行、问人挂起与续跑、预约复查、格式修复。

## 第二阶段合同

- 只扩展现有无头执行与定时任务，不造模型调度器。人打开任务的「允许接着跟进」才可自动续跑；默认关。
- 一份跟进授权明确最多轮数、最长天数、累计美元预算。每轮仍走现有隔离/连接/模型/授权；连接或授权变更使旧续跑失效，需人重新批准。不跨任务转移会话。
- 回执 `mesa-receipt` 只声明本任务 done / waiting / later 与剩余工作。waiting 必须在原目录留人工请求；问人后退出执行进程，回答由 Mesa 持久投递后才唤醒。不得自行答卡片、扩大权限、开流程步骤或采纳。
- later 为同一任务一次预约，RFC3339 时间、稳定键、用途；限授权有效期与轮数。机械复查只调用人配置的项目内探测脚本，Agent 不能交命令；未满足条件不调 AI。规则仍由人写。
- 业务输出先保存；回执格式错误最多确定性修一次，只为完整 JSON 补闭合代码块，不调 AI 猜字段、不进入项目目录、不调用工具。修不好保留原结果，交人核对，不把格式错误当业务失败重试。取舍：少修几种坏 JSON，换取不增加花费与权限风险。
- 常驻核心复用本应用二进制的独立无窗口入口，默认关；只处理人已授权的后台任务，桌面退出只回收桌面执行，不回收核心。关闭后台选项/更新/卸载时先停止核心、回收子进程。单实例 OS 锁，只有本机私有控制记录，不开放公网。
- 后台是本机进程：电脑关机/睡眠不能运行；未搬走的交互终端/手机窗口逻辑不宣称具备后台能力。核心完成与失败持久记账，桌面按记录刷新；所有成果仍回桌面评审。

## 事件批次

- 在 `schedules.json` 同一次原子写中，把待处理事件移到在途批次，保存触发依据；新事件继续入待处理队列。
- 调 CLI 前把执行 Run 关联到批次；关联失败不得执行。
- 运行历史和批次收尾同一次原子写：成功消耗批次，失败退回原事件，取消保留并暂停；同一个 Run 回执不能重复计历史或失败数。
- 每个后台 tick 在任务 OS 锁及项目锁内核对遗留批次。尚未关联 Run 的只做过准备，可退回；已经关联 Run 而未收尾的不明结果暂停、保留事件和依据，不自动重新执行。
- 存储错误不能伪装完成，保留在途记录供下轮恢复。锁顺序仍为任务锁 → 项目锁 → 配置叶子锁。

## 人工回答

- 人点「交给 Agent 继续」才把所选条目的问题与回答快照存到配置目录，不以打开标签或安排启动为已送。
- 绑定发问工作目录的原执行身份（Agent/会话）；终端空闲、无草稿且非只读时才领取。
- 领取先记发送中；聊天发送链成功后只确认这批中的原回答，其他已答条目不动。
- 进程异常退出、输入超时或确认失败不能证明没发出，留为待核对，不自动重复发；人核对原对话后明确重发才重新排队。
- 回答快照经后端脱敏；文件仍用 `.ccode/help-wanted.md`，不另造人工请求格式。队列仅由 Mesa 写，Agent 不能自行回答或确认送达。

## 验收

在隔离配置目录和临时项目执行真实文件读改写测试：领取后重开文件、新事件并入、重复收尾、未执行恢复、执行不明暂停；两条已答问题只投递其中一条、重复准备、领取后重启不重发、改答不误标、跨目录/Agent/会话拒绝确认。
前端测试确认发送成功才确认、失败不确认；运行前后审查 diff，不触碰其他会话改动。
