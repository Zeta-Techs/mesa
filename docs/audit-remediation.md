## 3. 明确未做、且不作为本次审计必须项

不要为了「收口」去做这些：全面拆大文件、合并两套 worktree、换框架、统一改写存储层。

尚未落地的优化（不阻塞审计修复本身）：

- 其他数据库入口仍反复 schema 检查；事件未形成完整批量事务
- 可见终端输出背压不是严格容量上限；缺压力测试
- 诊断丢弃没有计数与明确提示
- 冻结证据/备份没有保留期限与安全清理入口
- 没有冷启动/千级会话/多高输出终端/大 PDF 的可复现基准
- 没有「CLI 版本 × 平台 × 启动/恢复/取消/权限」持续集成矩阵（本地有 `e2e_channel` 真 CLI 端到端，三平台同一份；搬进 CI 要先解决各家 CLI 首次启动状态的种子，见 architecture §10 两端完善批「没做」）
- 冲突拒绝覆盖后，没有一键对比/另存/三方合并

## 4. 本轮补上的入口（相对「定时/预览已修、其它入口未修」）

- **普通目标采纳**不再逐文件 `fs::copy` 后无法回滚：先锁、备份原件、写入前核对基线，后一文件失败则回滚已写文件。主仓在采纳期间被改过的文件 fail-closed。
- **任务书弹层**与决策落盘、文献来源同步、播种 TASK.md 均携带 `expectedRevision`。外部改稿冲突时不覆盖；保存期间继续输入保持 dirty。
- **连接创建/修改**在密钥、网关、绑定之间失败时回退已写清单，并让密钥清除失败回到调用方。
- **Run 关闭**在数据库失败时仍释放 lease，并写诊断；不把忽略错误当成登记成功。

以上仍是乐观并发 + 成对回退，不是跨文件崩溃原子事务，也不锁住不走 Mesa 的外部编辑器。
