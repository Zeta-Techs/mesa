# Mesa 设计稿：项目内协作——看一眼、传话、协调与并行三层

> 状态：**2026-11-03 已拍板**（用户「按你推荐」两次：协作四条、并行规则改写三层；architecture §10 同日条）。
> 一期「看一眼」三件套已落地（见 §6）；二到四期待做。细则随各期写进 `docs/conventions/agent-workbench.md`「项目内协作」。

## 0. 一句话

同一个项目里同时有好几段 AI 在干活（流程步骤、目标、对话），今天它们互相看不见：写稿那一步不知道分析那一步刚改了表，
人只能自己来回传话。借 Grok Bot 的做法（一个协调员 + 几个工作者、只读的「看一眼」、结果分档异步回来），
让它们**先能看见彼此，再能传话**；同时把「并行只来自人声明或模板」改写成三层，给将来的协调对话留出路。

## 1. 参考：Grok Bot 怎么做（本机 Grok Bot.app 0.78.1 包内代码，只读查看）

| Grok Bot | 说明 | Mesa 取舍 |
|---|---|---|
| 协调员不干活，`send_task` 派活（可点名工作者，改写成任务说明、保留全部约束，超长退回不截断），只拿回执 | 人只跟协调员说话 | 三期：协调对话只**起草**，人点一次才开 |
| `work_landed`（确认 / 进展 / 结果）与 `work_overheard`（过程笔记）异步回来；只有进展与结果开口，其余归档；没新东西 `stay_silent` | 结果分档 | 并进「少占注意力」的通知分档 |
| `peek_changes` / `peek_runs` / `peek_agents`：只读看改动（加减行数与片段，不读整个文件）、命令与测试、同项目工作者状态 | 问状态不打断工作者 | **一期**：看改动 / 看运行 / 看同伴 |
| `switch_agent`：把对话切到某个工作者再切回 | | Mesa 工作台本来就能切标签，不另做 |
| `search_conversations` 只搜「你和这个人」的历史；别的 agent、别人、别的应用里的信息一律派活去取 | 记忆有边界 | 跨项目不直连（§2 第 4 条） |
| 授权「仅这次 / 这个 bot 一直 / 团队所有 bot 一直」 | | 「以后同类照此办」的适用范围分三级（后续） |

## 2. 拍板（2026-11-03）

1. **项目内传话自动送达**：同一项目里一个工作者可以给另一个留话，等对方下次空闲时经原对话送达；**全部留记录、工作台看得见、能撤回**。
2. **协调对话只起草**：每个项目可以有一个协调对话，能看一眼、能汇总，派活只出**方案草稿**，人点一次开齐；不替人回答人工请求（「Mesa 不替人自动回答」照旧）。
3. **跨项目不直连**：项目之间的规则、数据、密钥范围不同，跨项目共享只经「提升到研究档案」或人转发。
4. **并行规则改写成三层**（取代 v3.5「否决自动拆任务」的一刀切写法）：
   - **Run 内部不限制**：CLI 自己的子 agent 照常用，Mesa 只记事实（用了几个、花了多少），不干预。
   - **AI 提议拆分、人批准一次**（主路）：方案写明分几路、每路读什么交什么、写不写共享文件、预算多少、按什么拆（拆分本身若是科研判断要写出来）；
     人点「开」，Mesa 一次开齐。「人声明」从「人亲手开每一路」变成「人批准一份方案」，问责仍在人。
   - **免批准的自动展开只限模板 / 任务包声明过、且能机械分片的**：几路由数据决定（几篇文献就几路），不由 AI 判断；每路只写自己的文件；
     有预算上限；合成一次评审。
   - **模型路由仍不做自动**：模板 / 任务包可以写明某步用哪家哪个模型（人写的选择）；Mesa 不按任务特征自动换模型（研究记录要说清谁用什么做的）。
   - 再往前（AI 不经批准自己拆）的前提：核验可靠到评审成本降下来、有预算闸门、有能看全局的协调对话。到时另行拍板。

## 3. 为什么先做「看一眼」

- 只读，不碰任何拍板边界；传话、协调、拆分方案都要先「看得见」。
- 数据现成：Run 表（`app.db runs` / `run_events`）、核验记录（`.ccode/checks/*.jsonl`）、人工请求（`.ccode/help-wanted.md`）、工作树的 git 改动。

## 4. 一期：看一眼三件套

**走法**：`mesa_helper peek <agents|runs|changes>`，与出图同一条路（随包 helper、九家 CLI 只要能跑命令就能用、不写任何 CLI 配置）。
Mesa 拉起 Agent 时注入 `MESA_PEEK_TOOL`（helper 路径）与 `MESA_RUN_ID`（这次对话的 Run）；helper 按 Run 找到项目，**只读**打开 app.db。
没有 `MESA_RUN_ID`（Mesa 外的终端）时按当前目录找属于哪个 Run；找不到就说明「不在 Mesa 拉起的对话里」。

| 子命令 | 给什么 | 不给什么 |
|---|---|---|
| `peek agents` | 同项目其他工作（不含自己）：做什么（步骤名 / 目标名 / 对话）、哪家 Agent、进行中还是已结束、开始时间、工作副本位置与分支、核验三档计数、等人回答的问题数 | 对话原文 |
| `peek runs [--worker X]` | 某个（或各个）工作的运行事实：开始 / 结束 / 退出码 / 关闭原因、最近事件、没通过的核验条目（状态、标题、落点） | 终端全文 |
| `peek changes [--worker X] [--file 路径]` | 不指定：各工作改了哪些文件、各加减几行；指定：改动片段（有行数上限），没跟踪的新文件列名字 | 整个文件内容（要看自己去读，工作副本路径已给） |

**边界**：只看同一项目；内部后台对话（`internal`）与登录标签不列；输出过 Rust 层脱敏；最近结束的只列 3 天内、最多 12 个；
不是 Git 工作树的写明「看不了改动，去评审页」。

**怎么让 Agent 知道**：流程步骤的任务书加一节「同项目的其他工作」（三行，说命令和用途）；`mesa_helper peek --help` 自带说明。
普通对话：项目说明（对话注入自动档，`project-context.ts`）在同项目有别的工作开着时多一句（2026-11-03 补；「不注入」与自定义模板不带）。

## 7. 二期落地记录（2026-11-03）

- **发件箱放发话方自己的工作目录**（`.ccode/outbox.jsonl`）：设计稿原写「项目 `.ccode/` 信箱」，但 Codex 等的沙箱只让写工作目录，

## 8. 三期落地记录（2026-11-03；入口同日已改，见 §11）

- **入口**：工作台项目分组下「协调对话」，开 / 回到这个项目唯一的协调对话（`reuseKey = coord:<项目>`，项目根、项目说明照常附上）。
  开场指令（`split-plan.ts buildCoordinatorPrompt`）：不自己干活；看一眼答进展、tell 转告；人要拆分时按固定格式写项目根 `.ccode/split-plan.md`，
  写完让人去工作台批准，不自己开工；不替人答人工请求、不建议换模型；一次最多 6 路，每路只写自己的产物，拆不开就说按顺序做。
- **方案格式**：`# 拆分方案：总目标`、`按什么拆`、`共享文件`，每路 `## 名字` + `要做 / 读 / 交 / 写共享文件 / 等 / 预算`；不认识的「名称：内容」行原样记成这一路的备注
  （不混进上一个字段）。检查分拦下（没有路、超 6 路、没名字、重名、没写要做）与提醒（没写按什么拆、没写交、写共享文件）。
- **批准**：拆分方案卡（`SplitPlanDialog`）逐路看、能勾掉；「批准」= 每路记成一条目标（整个项目进隔离副本、验收后写回）并用项目默认 Agent 一起开工；
  **写了「等」的那一路只记下不开**，前面几路验收后人在项目里点开始（开工整仓复制，就带上前面的产物）。方案移进 `.ccode/split-plans/<时间>-approved|declined.md` 留底。
  只有能记目标的项目（无流程科研、工作项目）能一次开；有流程的科研与编程照方案自己开。
- **Codex 0.166 干跑**：按开场指令先 peek、再写方案、最后说「去工作台批准」；拆成三批质控 + 汇总四路，汇总那一路自己写了「依赖：等前三路」。
  据此补了两处：不认识的字段不再接进上一个字段（原先「依赖」被当成「写共享文件」续行误报）；加「等」字段（认等 / 依赖 / 前置 / 等待），要等的只记下不开。
- **未验**：Mesa Dev 窗口里从工作台开协调对话、批准后几个标签一起起来；Claude Code / Kimi 当协调对话；Windows。

## 9. 四期设计稿：模板 / 任务包声明的步骤按数据分几路（2026-11-03，用户「按推荐执行」拍板：三件事全按推荐；已落地见 §10）

**要解决的**：精读一步要读三十篇，一个 Agent 从头读到尾要几个小时；数据清洗一步有五个批次。几路同时读 / 洗能快几倍，
但不能让 AI 自己决定怎么拆（并行三层第三层：几路由数据定、每路只写自己的文件、有预算上限、合成一次评审）。

**推荐做法：同一个工作区里分片，最后一路收尾**（不开几个工作区）：

| 环节 | 怎么做 | 为什么 |
|---|---|---|
| 声明 | 步骤合同加一个可选段 `[steps.fan_out]`：`items`（从哪个文件数条目，如 `papers/included.json` 里 decision=included 的 id）、`per`（每路几条）、`max`（最多几路）、`own`（每路只许写的路径式样，如 `notes/{id}.md`）、`merge`（收尾写共享文件的那一路要做什么） | 由模板 / 任务包写死，开工时按数据算几路，AI 不判断 |
| 开工 | 照常建一个工作区、一个任务书；Mesa 按条目数切成 K 路（K ≤ max），每路一个 Run 在**同一个工作区**里跑，任务书末尾多一节「本路只做这些条目：…，只写 `own` 里的文件，不碰共享文件、不提交」 | 一个工作区 = 一次评审、一份提货单，评审冻结与采纳不用改 |
| 收尾 | 各路都结束后，Mesa 再开一路「收尾」（或由第一路接着做）：读各路产物、写共享文件（`notes/index.json`、`references.bib`）、写验收摘要 | 共享文件只有一个写者，不打架 |
| 预算 | 开工弹层显示「这一步会分 K 路同时跑」；K 路按同一个连接计费，可设每步花费上限，超了停后面没开的路 | 钱看得见 |
| 评审 | 还是这一步一次评审；核验照常跑一遍 | 「合成一次评审」 |

**不推荐**：每路一个工作区再合并——每路都要冻结、评审、采纳，注意力翻 K 倍，合并还要处理同名冲突，等于把评审成本做大。

**要你定的三件事**：
1. 同意「同一工作区分片 + 收尾一路」吗？风险是几个 Agent 同时在一个目录里：要求各路不跑 git 提交、只写自己的文件；万一写了别人的文件，评审时照常看得见。
2. 第一批给哪几步加 `fan_out`？建议只先给**精读**（每篇一份笔记，最典型）一步，跑通再给数据清洗的「每批次」。
3. 开工时默认分几路？建议默认不分（开工弹层里勾「分 K 路同时跑」才分），先由人选，用顺了再改默认。

## 11. 协调对话并进工作台（2026-11-03，用户「按推荐改」拍板）

**起因**：用户点验时问「这个协调会话是干嘛的，还要重开一个终端」「这个问答直接放在工作台是不是更好」。核对后，协调对话做的三件事里两件用不着 AI：
进展本来就在 Mesa 的记录里，传话不必先说给 AI 再让它转；只有拆分要判断，而那是一次性的活，不需要一段一直开着的对话。

**定下的**（取代 §8 的入口与开场，方案格式、检查、批准不变）：

| 原来在协调对话里 | 现在 |
|---|---|
| 问进展（AI 跑 peek 再转述） | 工作台任务面板直接显示：此刻在做什么、这一轮跑了多久、花费（原有），加 **改了哪些文件**（`peek_changes`，与 `peek changes` 同口径） |
| 让 AI 转告某一段 | 任务面板 **给它留话**：Mesa 记进 `mail-state.json` 的 `from_you`（发话人是你，不经 Agent），与 Agent 之间的留话同一条送达 / 撤回链路；送进对话写「【你在 Mesa 工作台留的话，Mesa 转达】」 |
